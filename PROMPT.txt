讲稿我一直用 Markdown 写，汇报前再一页页往幻灯片软件里搬，搬烦了，想要一个浏览器里的写作台：左边敲 Markdown，右边即时看到切好页的幻灯片。前后端都请你来做。真正要较真的是后端那套把文本切页、再把每页解析成结构树的逻辑，以及它跟讲稿存储之间怎么咬合；界面做到顺手即可。

切页与解析规则：单独占一行、由三个或更多连字符组成的分隔线当作翻页符；页内要认出各级标题、有序与无序列表（含多层嵌套）、加粗与斜体、行内代码、围栏代码块、引用、链接和图片。产出是一棵结构化文档树，能说清第几页、页里有哪些块、每块什么类型、里面还嵌着什么，而不是拼好的 HTML。围栏代码块里的连字符行、井号一律当普通文字；列表嵌套层级照实保留，二级项不能被压成一级；同一段文本解析多少遍，结果逐字段相同。

写的人不会总那么规整：代码围栏忘了关、井号后面空着、分隔线紧贴正文没留空行、列表缩进混着空格和制表符。这些输入都不能让整篇崩掉或吞掉后文。至于每种情况怎么补救——比如没关的围栏是一路吞到文末，还是在下一个翻页符处截断——都有说得过去的不同做法，各有代价。请你自己定一套策略，在文档里讲明理由，并在解析结果里标出每一处容错的位置和用了哪种补救，让写的人知道哪里是被"猜"出来的。

编辑时不能每敲一个字就整篇从头来。改动提交给后端后，只重算受影响的页，没波及的页直接复用；可一处编辑可能新增或删掉翻页符，也可能打开或合上一个代码围栏，连带影响后面很多页，这些情形都得算对。硬性要求：任意一串编辑之后，增量得到的整篇结果必须与对最终文本做一次全量解析逐字段一致，页号、块结构、容错标注都算在内，我会用随机编辑序列对拍。响应里顺带告诉我这次实际重算了哪几页。

讲稿要落盘，每份带递增的修订号。前端自动保存，保存时捎上它所依据的修订号；如果服务端那份已经被别处（比如另一个标签页）改过，这次保存要被拒，并返回当前修订号与内容，前端提示冲突，让人选保留哪份或手动合并，绝不能悄悄覆盖。存储与解析也要对得上：按修订号取回的结构树，必须等于对那一版文本做全量解析的结果，增量缓存不能在不同修订之间串用。

接口需要覆盖：整篇解析、按页号取单页、提交编辑做增量解析、讲稿的新建、读取、带修订号保存和历史修订读取。空文本得到零页而不报错；过长或明显不是文本的输入给出明确错误。要写成自动化测试的有：重复解析结果相等、代码块里的分隔线不翻页、嵌套层级保留、残缺输入不崩且容错点有标注、增量与全量逐字段一致、拿过期修订号保存被拒。另外准备一份示例讲稿作回归基准：不少于三页，要有多层列表和至少一段代码块，它的解析结果固定下来写进测试。

前端用 React，左右分栏、可逐页翻看，页面内容全部来自后端解析，前端不另起一套 Markdown 解析；冲突时提示要清楚。后端跑在 Python 3.12 上、接口层用 FastAPI，讲稿存 SQLite 或文件都行。词法切分、翻页、块级与行内解析、容错、增量重算、讲稿存储、HTTP 接口和前端组件请拆到各自的模块与文件。前后端各一个容器，用一份 compose 文件拉起，浏览器打开就能边写边看。这一版的范围集中在解析、增量预览和讲稿保存三件事上。
